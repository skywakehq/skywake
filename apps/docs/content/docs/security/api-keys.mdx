Every call to the API needs a key. A key belongs to one organization and one environment, and has a role. Give each agent or tool its own key, with only what it needs, so you can see what it did and revoke it on its own.

The key is shown only once, so keep it right away. Pass it as `SKYWAKE_API_KEY`, as `key` in an SDK, or as a bearer token: `Authorization: Bearer sw_...`. You can also make one in the console under **Settings → API keys**.

## Sign in from the CLI

On your own machine, you don't need to copy a key at all:

```bash norun
skywake login
```

The CLI shows a code and opens the console at `/cli/CODE`. Check that the browser shows the same code, then allow it. The CLI makes the key itself and sends only its id, so the key never passes through the browser. It saves the key in `~/.config/skywake/credentials.toml`.

- Any member can allow a key for one environment, with a role up to their own.
- A key for every environment needs an organization admin.
- `skywake login --paste` saves a key you paste instead. `--profile NAME` saves it under another profile, and `--url` points that profile at another server, such as [your own](../self-hosting/local-api.mdx).

## Roles

Each role can do everything the role before it can, and more.

| Role    | What it can do                                                    |
| ------- | ----------------------------------------------------------------- |
| `read`  | Get, query, count and aggregate rows; list branches and versions. |
| `write` | Also upsert, update and delete rows; fork, merge and restore.     |
| `admin` | Also create, configure, copy and destroy indexes.                 |

Managing keys and reading the [audit log](./audit-log.mdx) need an organization admin.

If a key lacks what a call needs, the call fails with `PermissionError` (`403`), and the message says which role it needs. Creating an index, including by the first write to a new name, needs `admin`. That is why the example writes to `products` with the admin key before the agent writes to it.

## Environments and names

A key works in one environment, such as `prod` or `staging`. Requests with it go to that environment, and names like `products` mean the index in that environment.

`only` narrows a key to some indexes in its environment: names, or prefixes that end in `*`, such as `["products", "docs-*"]`. The default is every name (`["*"]`). A key can't reach more than the key that makes it.

An organization admin can make an **all-environments** key with `environment: null` (CLI `--all-environments`). Requests with it name the environment: `new Skywake({ environment: "staging" })`, the `SKYWAKE_ENV` variable, `--env` in the CLI, or the `Skywake-Environment` header. With none of these, they go to `default`.

<Callout type="warn">
  When an all-environments key makes a key without naming an environment, the new key is also an
  all-environments key, and `only` is ignored. Name the environment, as the example does.
</Callout>

## Fields

| Field                                      | Meaning                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------ |
| `name`                                     | 1 to 100 characters.                                                                 |
| `role`                                     | `read`, `write` or `admin`.                                                          |
| `environment`                              | The environment it works in. Null for every environment. The maker's own by default. |
| `only`                                     | Up to 50 names or prefixes. `["*"]` by default.                                      |
| `expiresInDays` (Python `expires_in_days`) | 1 to 3650. Without it, the key does not expire.                                      |

A key made with another key never outlives the key that made it.

A key belongs to the person who made it in the console. When that person leaves the organization or is removed from it, their keys are revoked, and so are any keys made with those keys.

## List and revoke

Listing keys never returns the keys themselves. It returns each key's `id`, `name`, `role`, `environment`, `only`, `expires`, `last_used`, `created`, and who made it:

- `created_by` is `user:ID` for a person in the console, or `key:ID` for a key made with another key.
- `created_by_email` is that person's email.
- Both are empty for the first key of an organization.

Revoking a key takes effect at once. Over HTTP, keys are `GET /v2/keys`, `POST /v2/keys` and `DELETE /v2/keys/{id}`, and `GET /v2/whoami` shows what the current key may do.

<Callout type="info">
  Keys look like `sw_...` and end in a checksum, so secret scanners can spot a leaked one.
</Callout>

Making and revoking keys is recorded in the [audit log](./audit-log.mdx).
