## Diff

`work.diff("main")` (CLI: [`skywake diff app@agent-1 [main]`](/reference/cli/diff)) lists the paths that differ between the branch and another branch or commit, each with its `change`: `added`, `removed` or `modified`. The CLI marks them `+`, `-` and `~`. A folder that is new on one side shows up once, not file by file. Folders that didn't change are skipped without being read, so a diff costs as much as what changed, whatever the size of the tree.

The comparison is with the other branch as it is now, so changes made on `main` since the fork show up too.

## Merge

`work.mergeInto("main")` (CLI: [`skywake merge app@agent-1`](/reference/cli/merge), `--into` for another branch) brings the branch's changes into another. It is a three-way merge against the newest commit both branches share.

- When both sides changed a text file in different places, the changes are merged line by line.
- A file's mode is merged on its own, apart from its content.
- When changes overlap, nothing is saved and the merge fails with `MergeConflict`. Its `conflicts` lists the paths. The CLI prints `conflict: PATH` for each and exits non-zero.

| Option    | CLI         | Meaning                                                                                    |
| --------- | ----------- | ------------------------------------------------------------------------------------------ |
| `message` | `-m`        | The merge commit's message.                                                                |
| `dryRun`  | `--dry-run` | Only report the conflicts the merge would have now. Saves nothing.                         |
| `prefer`  | —           | Settle every conflict by keeping `into`'s side (`ours`) or the merged branch's (`theirs`). |

The result is `{ commit, conflicts }`. Merges into one branch take turns, like any other write.

## Settle conflicts yourself

To combine both sides instead of picking one, merge the other way first, then write the result on the fork:

1. Try the merge. On `MergeConflict`, read each conflicting path on both branches and decide what it should hold.
2. Merge `main` into the fork with `prefer: "ours"`. The fork now includes `main`, keeping its own side of each conflict.
3. Write the settled files on the fork, and merge it into `main` again. This time nothing overlaps.

<include lang="ts">../../../examples/filesystem/resolve.ts</include>

`combine` is your own code, such as an agent that reads both versions and writes one.

Per-path choices in a single merge request (`resolve`, with `take`, `text` or `delete` for each path) exist only on the v1 API, [`POST /v1/namespaces/{namespace}/merges`](/reference/api/history/mergeBranches). `/v1` goes away one release after v2.

## Undo

<include lang="ts">../../../examples/filesystem/undo.ts</include>

- `app.revert(commit)` undoes one commit by adding a new commit that puts back what it changed. For a merge commit, it goes back to the first parent. If later commits changed the same paths again, nothing is saved and it fails with `MergeConflict`.
- `app.restore(commitOrTime)` makes the branch look like it did then, as one new commit on top. The commit can come from any branch of the disk. In TypeScript a `Date` picks the newest commit at or before that time.
- `read`, `list`, `grep`, `find` and `download` take `at` to look at the past without changing anything.

Both return `{ commit, changed }`. `changed` is `false` when there was nothing to undo. Both need a `write` key. A [protected branch](./protection.mdx) refuses both, because it changes only through a merge. There is no CLI command for revert or restore yet; use an SDK or `POST /v2/disks/{disk}/revert` and `/restore`.

## History

`app.log({ path, limit })` lists commits newest first: each has an `id`, a `message`, when it was `created`, and for a merge, the commit it `merged`. Pass `path` to see only the commits that changed one file. In the CLI it is [`skywake log app@agent-1 --path src/app.py --limit 10`](/reference/cli/log).
