Use your own vectors when you embed with your own model, or search things that aren't text, such as images. Put the vector in a field of each row, and query with `vector`.

The hits come back nearest first:

```json
[
  { "id": "cat.jpg", "score": 0.99, "label": "cat", "width": 640 },
  { "id": "fox.jpg", "score": 0.83, "label": "fox", "width": 800 }
]
```

- A list of numbers in the first rows becomes a vector field, `cosine` by default. Its length is the dimension. To choose the metric or the element type, [create the index](./create.mdx) with a [schema](./schemas.mdx#vectors).
- When rows bring a vector, the index doesn't embed their text, so a string query has no meaning to search. Query with `vector`, or with `mode: "keywords"`.
- `query({ vector })` uses the vector field whose dimension matches. A vector of another length is an `InvalidRequest` error.
- `score` is `1 - distance`, so larger is closer. With `cosine` it is the cosine similarity.
- Vectors are never returned with hits or by `get`.

## Options

| Option   | Default                 | Meaning                                            |
| -------- | ----------------------- | -------------------------------------------------- |
| `vector` |                         | Your vector; skips embedding.                      |
| `limit`  | `10`, at most 1000      | Hits to return.                                    |
| `filter` |                         | Only rows that pass. See [filters](./filters.mdx). |
| `fields` | every field but vectors | Which fields come back with each hit.              |
| `branch` | `main`                  | Set on the handle: `sky.index(name, { branch })`.  |

In the CLI these are `--vector '[...]'`, `--limit`, `--filter` and `--fields`. Over HTTP it is `POST /v2/indexes/{index}/query` with the same fields.

## Recall

The index groups vectors into clusters. A query reads the clusters nearest to its vector, enough to find about 95% of the true nearest rows. Rows written since the last build are always searched exactly.

## Builds, recall checks and warming

A build clusters the rows written so far, so that queries have less to read. Builds start in the background once enough has been written, and you can keep writing and querying while one runs.

v2 has no call yet to start a build, measure recall, warm the cache, set a recall target or `probe`, or keep a few hits per group (`per`). The `/v1` routes do these, and go away one release after v2:

<include lang="bash" meta='tab="HTTP"'>
  ../../../examples/indexes-1/build.sh
</include>

- `build` and `warm` return an operation. Follow it with `GET /v1/indexes/{index}/operations/{id}`; its `status` is `running`, `done` or `failed`.
- `recall` picks rows at random and queries with their vectors twice, once as usual and once exactly, then compares the two. Each pair counts as two queries in your usage.
- `warm` starts reading the branch into the cache. Call it shortly before queries arrive, for example when a user opens your app.
