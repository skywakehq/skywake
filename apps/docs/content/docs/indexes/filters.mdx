The same filter works in `query`, `count`, `aggregate`, `rows`, `update` and `delete`. A query with a filter and no text lists the matching rows.

## Shape

A filter is an object whose keys are keywords or field names:

| Form                       | Holds when                  |
| -------------------------- | --------------------------- |
| `{ field: value }`         | The field equals the value. |
| `{ field: { op: value } }` | The comparison holds.       |
| `{ and: [f, ...] }`        | Every filter holds.         |
| `{ or: [f, ...] }`         | Any filter holds.           |
| `{ not: f }`               | The filter doesn't hold.    |
| `{ id: { op: value } }`    | The row's id compares.      |

When one object has several keys, all of them must hold. A row that doesn't have the field fails every comparison on it.

## Operators

| Op                             | On                  | Value                         |
| ------------------------------ | ------------------- | ----------------------------- |
| `eq`, `ne`                     | any filterable type | one value                     |
| `lt`, `lte`, `gt`, `gte`       | any but `bool`      | one value                     |
| `in`, `not_in`                 | any filterable type | a non-empty list              |
| `contains`                     | lists               | one value                     |
| `contains_all`, `contains_any` | lists               | a non-empty list              |
| `glob`, `iglob`, `regex`       | strings             | a pattern                     |
| `fuzzy`                        | strings             | `{ text, edits, ignoreCase }` |
| `exists`                       | any field           | `true` or `false`             |

- On a list field (`strings`, `ints`, `numbers`), an operator holds if it holds for any item. `contains` holds when the list has the value; to match several items, use `contains_all` or `contains_any`.
- `iglob` is `glob` that ignores case.
- `fuzzy` holds when the whole value is within `edits` (0 to 2, 1 by default) of `text`. One edit is a letter added, removed or changed, or two letters swapped. `ignoreCase` is `false` by default.
- `exists: true` holds when a row has the field, `exists: false` when it does not.
- `bool` takes only `eq`, `ne` and `in`.
- `datetime` takes an RFC 3339 time or milliseconds since 1970.
- `id` takes `eq`, `ne`, `in` and `not_in`, and also `lt`, `lte`, `gt` and `gte`, which compare in id order. Numbers sort before strings.
- `sparse` and `vectors` fields can't be filtered.
- A `text` field takes the operators of a string on its whole value when it is `filterable`, which inferred text fields are. With `mode: "keywords"` it also takes [text filters](./full-text.mdx#text-filters) such as `phrase`.

## Sort by a field

To list rows in the order of a field instead of by score, pass `sort` and no text. The keys of `sort` are fields, or `id`, each `"asc"` or `"desc"`; later keys break ties.

## In the CLI

`skywake query --filter` takes filters written as words, which are quicker to type than JSON:

```text
category = shoes and price < 130
(category = hats or price >= 120) and not in_stock = false
category in (hats, shoes, 'rain gear')    category not in (bags)    category != hats
```

The operators are `=`, `!=`, `<`, `<=`, `>`, `>=`, `in` and `not in`. A value is a number, `true`, `false`, a word or a quoted string. `and` binds tighter than `or`. For the other operators, pass JSON in the object form, as in `'{"tags": {"contains": "sale"}}'`.

## Errors

If a filter doesn't fit the schema, the call fails with `InvalidRequest`, and the error's `path` points at the bad part, such as `filter.price.lt`.

## Filter-first search

A search by meaning with a filter normally walks the nearest clusters and drops the rows that fail the filter. That does a lot of extra work when the filter matches very few rows, for example one tenant out of many. In that case the query can instead read just the matching rows.

Turn this on per field with [`filter_index`](./schemas.mdx#filter-index), in the schema or later with `configure`:

```json title="PATCH /v2/indexes/products"
{ "attributes": [{ "name": "tenant", "type": "string", "filter_index": true }] }
```

The next build creates the filter index. After that, a query reads only the matching rows when all of these are true:

- every field its filter names has `filter_index`,
- the filter, or one part of its `and`, is an `eq`, `in`, `lt`, `lte`, `gt` or `gte` on one of them, and
- that part matches about 0.3% of the built rows or fewer (the cutoff is never below 4,096 rows or above 100,000).

Otherwise the query runs as usual. Either way, every hit passes the whole filter.
