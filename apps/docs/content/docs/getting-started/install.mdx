Most people start with the CLI from npm, then sign in:

```bash norun
npm install -g skywake
skywake login
```

## The CLI

The npm package ships prebuilt binaries for Linux on x86_64 and arm64 (glibc). npm installs only the one for your machine. You need Node 18 or later. To run it without installing, use `npx skywake`.

On any other platform, build the `skywake-cli` crate from source:

```bash norun
cargo build --release -p skywake-cli    # target/release/skywake
```

## The SDKs

```bash tab="TypeScript" norun
npm install skywake
```

```bash tab="Python" norun
pip install skywake
```

The `skywake` npm package is the TypeScript SDK and the CLI. Go, Rust, Java, C# and Ruby SDKs have the same indexes and verbs. See the [SDK reference](/reference/sdk).

## Sign in

```bash norun
skywake login
```

[`skywake login`](/reference/cli/login) signs you in through the browser. It shows a code and opens the console at `/cli/CODE`. Check that the console shows the same code, choose the key's role and environment, and allow it. The CLI then saves a new key for you.

To use a key you already have, run `skywake login --paste` and paste it, or set `SKYWAKE_API_KEY` before you run `skywake login`. Make keys in the console under Settings → API keys, or see [API keys](../security/api-keys.mdx).

[`skywake whoami`](/reference/cli/whoami) shows the key's organization, environment and role. A key belongs to one organization and one environment, so you never name the environment again. An organization admin may make a key for every environment. With one of those, pick the environment with `skywake env staging`, `--env`, `SKYWAKE_ENV`, or `environment` in the SDKs.

## Where settings come from

The SDKs, the CLI and the MCP server read their settings the same way. The first match wins:

| Setting     | Code          | Env var           | Credentials file     | Default                   |
| ----------- | ------------- | ----------------- | -------------------- | ------------------------- |
| key         | `key`         | `SKYWAKE_API_KEY` | from `skywake login` | none                      |
| URL         | `url`         | `SKYWAKE_URL`     | per profile          | `https://api.skywake.dev` |
| environment | `environment` | `SKYWAKE_ENV`     | per profile          | the key's own             |
| profile     | `profile`     | `SKYWAKE_PROFILE` | none                 | `default`                 |

With no key, the error says to run `skywake login` or set `SKYWAKE_API_KEY`.

The credentials file is `~/.config/skywake/credentials.toml` (on Windows, `%APPDATA%\skywake\credentials.toml`), readable only by you. It has one table for each profile:

```toml
[default]
key = "sw_..."

[local]
key = "sw_..."
url = "http://localhost:8080"
environment = "dev"
```

A self-hosted server is a profile with its own `url`. Sign in to it with `skywake login --profile local --url http://localhost:8080`, then pass `--profile local` or set `SKYWAKE_PROFILE=local`.

## The MCP server

```bash norun
skywake mcp
```

[`skywake mcp`](/reference/cli/mcp) runs the MCP server, which gives an agent tools to search and write indexes. It runs on Node, so it works anywhere `npx skywake mcp` does, and `uvx skywake mcp` starts the same server from the Python package. It reads the settings above. For example:

```json
{
  "mcpServers": {
    "skywake": {
      "command": "npx",
      "args": ["-y", "skywake", "mcp"],
      "env": { "SKYWAKE_API_KEY": "sw_..." }
    }
  }
}
```

See [MCP](../mcp.mdx) for its tools.
