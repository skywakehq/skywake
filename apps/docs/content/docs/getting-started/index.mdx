Skywake stores **disks**: shared folders of files, with branches and history, that agents read, write and mount.

You get a disk by its name, such as `app`, and call a few verbs on it. A disk can be **forked** into an instant copy and **merged** back. A fork copies no data, however big the disk is.

## Disks

A branch of a disk is a whole folder tree with its history. Every disk starts with `main`. Forking a branch writes one small object, so if a hundred agents each fork the same 20 GB disk, you store about 20 GB plus whatever they change.

You can work with a disk in several ways:

- With the SDKs and the CLI: `read`, `write`, `list`, `grep`, `find` and `query`, over HTTP, with nothing to mount. [`skywake upload`](/reference/cli/upload) saves a folder as one commit and [`skywake download`](/reference/cli/download) copies a branch to a folder.
- On Linux, [`skywake mount`](../filesystem/mount.mdx) serves a branch as a live folder. Files are fetched chunk by chunk as they are read, and changes are saved every 2 seconds.
- From agents, through the [MCP server](../agents/mcp.mdx) or the [bash tool](../agents/bash.mdx).

When a fork is ready, you [merge](../filesystem/diff-and-merge.mdx) it back. The merge is three-way, and text files are merged line by line. If both sides changed the same lines, the merge lists the conflicting files and saves nothing.

## Search

Search is a switch on a disk. Make the disk with search on (`skywake create disk app --search`), or turn it on later, and `app.query("where is auth handled")` finds files by meaning and keywords. See [search](../filesystem/search.mdx).

## Environments and keys

An organization has environments, such as `prod`, `staging` and `dev`. Each is a separate world of disks and keys, so `app` in `prod` and `app` in `staging` are different disks. A key belongs to one environment, so a name alone says which disk you mean. See [install](./install.mdx) to sign in.

## How it sits on object storage

Skywake keeps all of its data in object storage. Your machines hold only a cache, which you can throw away at any time. A disk's folder in the bucket looks like this:

```text
chunks/<blake3>          file content, split at content-defined boundaries
commits/<blake3>         commits
objects/<blake3>         packs of trees (directories)
refs/<branch>            the branch head: its current commit
```

- Files are cut into chunks (FastCDC, about 1 MiB on average), compressed with zstd and named by their BLAKE3 hash. Identical data is stored only once, across every file and branch.
- Folders are stored as trees named by the hash of their contents. A diff can therefore skip every folder that didn't change.
- Branch heads are the only objects that ever change. Moving a head is a conditional write (`If-Match`), so when two writers race, exactly one of them wins. Skywake needs no other locking.
- Any object storage with conditional writes works, such as AWS S3, Cloudflare R2 or RustFS. A local folder works too.

## The pieces

| Piece        | What it does                                                                   |
| ------------ | ------------------------------------------------------------------------------ |
| `skywake`    | The CLI: disks, branches, search, mounts, keys, and `skywake mcp` for agents.  |
| `skywaked`   | One daemon per Linux machine. It runs every mount and its chunk cache.         |
| API          | Organizations, environments, keys and disks. Postgres holds the control plane. |
| Console      | The web app: sign-in, the fork tree, merges, API keys.                         |
| SDKs and MCP | Clients for the API in seven languages, and an MCP server for agents.          |
